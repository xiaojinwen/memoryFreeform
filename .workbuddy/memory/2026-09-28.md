## fix169：开窗大小从不认上一次拉伸的尺寸（已修复 + 真机验证）

### 现象
用户报「打开小窗的大小还是没有用到上一次大的」。此前 fix168 已处理过 BAR-UP 误判关闭，
设备实测已是 `versionCode=169`（168 确实装上了，不是没安装），`rememberSize=1`（开关是开的）
——所以既不是"没装",也不是开关问题。

### 取证（决定性的一张表）
读 `/data/system/memoryfreeform_window_memory`，**每个包的宽高全都一模一样**：

```
com.tencent.mm=187,354,1267,2082        → 1080x1728
com.miui.calculator=295,672,1375,2400   → 1080x1728
mark.via=125,588,1205,2316              → 1080x1728
com.coolapk.market=324,127,1404,1855    → 1080x1728
（横屏四条全部 1080x1388，位置都一样）
```

→ **只有位置在变，尺寸永远不变**。配合 `record.state`：

```
Task.resize            calls=0 applied=0   ← 指定的 RESIZE 通道零调用，是死路
Task.onResize          calls=6 applied=2 skip=no-pkg
Task.onMovedByResize   calls=7 applied=7   ← 唯一能写盘的（= 拖动）
Task.setBounds         calls=84 applied=16 skip=not-freeform
```

### 根因（结构性的）
写入白名单只剩两条：`onMovedByResize`（拖动）+ `Task.resize`（我们自己的 am resize）。
而 `setBounds`/`onResize` 被策略性 skip-write（fix74/fix75 为了避免系统重摆帧污染），
**MIUI 缩放把手走的回调链既不经过 `Task.resize`（零调用），也被 setBounds/onResize 的
skip-write 挡在外面**。控制流上 475 行那一进来就包住、519 行直接 return，走到不了
567 行的 bar-drag 即时落盘。

结果：拉伸帧一次都没进过 `latest`，写进记忆的永远是「上次开窗的下发几何」自我循环；
拖动反而正常，所以位置会变、尺寸不会变。

### 修法（169）
**不猜澎湃用哪个回调回调改的尺寸** —— 手势结束那一刻直接读窗口真实几何：

- `flushTerminalAsMove()`：优先 `boundsOf(freeformSeen[pkg].task)` 读实时 bounds，
  `latest` 只做兜底。（原来只看 buffer，buffer 里可能只有手势中途帧/压根是空的）
- `barUpJudge()` 第二次采样（#1，已摆定）确认为「移动」后，再按实时几何落一次，
  确保这一次手势拉出的新尺寸一定进记忆。

文件：`hook/MiuiFreeformRecordHook.kt`；版本 → `versionCode=169 / 1.0.169`。

### 真机验证（61ec0d27，重启后钩子重新加载）
用 `am task resize` 做可控尺寸变更 + 轻点触发抬手落盘，走完整往返：

```
resize 前 bounds: [324,987][1404,2715]  尺寸 1080x1728（默认）
resize 后 bounds: [324,987][1200,2200]  尺寸 876x1213  ← 尺寸确实变了
轻点后记忆:        mark.via=324,987,1200,2200          ← 新尺寸被记住 ✅

再冷开:
memory:  mark.via=324,987,1200,2200
bounds:  [324,987][1200,2200]          ← 按记忆恢复，不再是默认 1080x1728 ✅
```

探针也确认新代码在跑：`BAR-UP flush(移动·实时) pkg=mark.via 记=324,987,1404,2715 尺寸=1080x1728`。

### 待确认
 synthetic swipe 抓不到缩放把手热点（只把窗口挪了 1px），**手指真实捏握拉伸**没能自动化复现。
逻辑上任一步都会在抬手 ~2.5s 后被实时读数捕获，但需用户手动拉一次最终确认。
测试污染：`mark.via` 的记忆现在是 876x1213（可自行拖回）。

## fix170：追究「为什么拖动不记录大小」→ `isTouched` 是单点钥匙（代码已改，待用户真手势验证）

用户追问「为啥我拖动不会记录大小」，并要求解释 `isTouched` 为什么会失效。

### `isTouched` 的四个失效环节（代码 + 探针双向确认）
`isTouched(pkg, 2s)` = `lastTouchTs[pkg]` 距现在 < 2s，而 `lastTouchTs` **唯一**的写入点
是 `onPointerEvent(ACTION_DOWN)`，写之前要连过四关：

1. **懒注册的全局 PointerEventListener 必须成功**（`ensurePointerListener(task)` 反射找
   `WindowManagerInternal.register*`）——失败则 DOWN 一个都收不到。
   探针 `bar(... plisten=1)` 说明本机这关是通的，排除。
2. **DOWN 那一刻 `freeformSeen` 里必须有这个包**（`for ((pkg, s) in freeformSeen)`）——
   探针里成群出现 `=== BAR-DOWN seen= ===`（seen 为空），即**循环体一次都没进**，
   `lastTouchTs` 在这次手势里完全没刷新。窗口刚 remove / 走 `writeSnapshotAsClose`
   （1060 行 `freeformSeen.remove`）会让它空，直到下一次 resize 回调才补回来。
3. **且 `isFreeformTask(s.task)` 为真** —— 已知 `getWindowingMode()` 会在动效瞬间抖到
   mode=1（fix168 就是被它坑过），按下撞上抖动窗口就是 `no-ff`，第一次天堂 samp。
4. **只有 2 秒窗口，且只在 DOWN 那一刻刷新一次**：慢动作拖缩放把手很容易超过 2 秒，
   后半程 + 全部结束后续帧的 `touched` 已经是 false。→ **最可能在真机上反复发生的**一条。

### 后果
尺寸写入的唯一放行条件是 `if (sizeChanged && touched)`（fix91，509 行），后面的
`setBounds`/`onResize`/`resize` 全部 `return`。所以 touched 一失效，**用户拉出来的
尺寸被永久拒收**，而位置走 `onMovedByResize`（Src.MOVE，不看 touched）照样写 ——
"位置会变、大小从不变化"，与记忆文件里「所有包都是 1080x1728」完全吻合。

### 修法（170）
不再把 `touched` 当唯一钥匙：
- 新增 `RESIZE_SIZE_TOL_NO_TOUCH = 32`：**无触摸证据**时要大幅才会被认成拉伸
  （系统重摆/输入法通常只改坐标、即便改尺寸幅度也小），隔开误伤。
- 新增受控放行：非失焦角 + **不在出生安静期**（2s，否则侧边栏开窗的系统默认几何会被
  当成"用户拉伸"写回去，反而制造「重开又变回默认」）+ 幅度够大 → `scheduleWrite(Src.RESIZE)`。
  坐标仍由 doWrite 的 fix80 保护：此刻无触摸 ⇒ 沿用旧坐标、**只更新尺寸**。
- ★ **补取证盲区**：原来只有 `onResize` 打探针，`Task.setBounds`（`calls=181`，全场最密）
  连一条痕迹都没有 —— 用户拉伸若走 setBounds，此前根本看不到。现三个尺寸类回调
  **全都**打 `methodName(skip) szChg=... big=... touch=... base=WxH`，一次真手势即可定死链路。

文件：`hook/MiuiFreeformRecordHook.kt`；版本 → `versionCode=170 / 1.0.170`。
已构建安装 + 重启（钩子心跳刷新，61ec0d27），**待用户真实拉伸手势验证**。

## fix175：缩放改「实时记录」+ 跟手优化

### 用户两次质疑（都对）
1. 「拖动改变大小后很慢才生效，有时候甚至不会生效」
2. 「既然拖动有实时反馈，为什么落盘要等 UP 后 900ms/2.5s 采样？直接实时写不行吗？」

### 处理
- **跟手优化**：fix174 每帧 5 次 `XposedHelpers` 反射查找，拖动时一帧走好几个回调 →
  开销落在跟手帧上。改为缓存 `mMiuiFreeFormManagerService` 实例 + 两个 `Method`，
  且同一 task **120ms 内复用**读值（缩放是连续量，不必逐帧读）。
- **缩放改纯实时**（关键）：缩放是**只有用户拖才会变**的干净连续量 —— 系统重摆 / 关闭
  动效只改坐标、改不动缩放，所以它**不需要 bounds 那套防污染闸门**。
  `maybeRecordScale()` 的调用条件去掉 `isTouched` 要求，并在 `onMovedByResize` 帧上也调，
  「变了就记」，不再等 BAR-UP 判定、不再等 2.5s 采样。

### ★ 澄清（回答用户第 2 问，别再搞混）
**bounds 在拖动过程中本来就是实时落盘的**：`bar-drag` 分支直接
`scheduleWrite(Src.MOVE)`（80ms debounce 合并连帧），探针里 `bar-drag write` 后紧跟
`WRITE MAIN` 就是证据。抬手后的 900ms / 2.5s 两次采样是**纠正环节**而非写入环节 ——
它用来区分「移动 / 关闭 / 重开」，把关窗动效帧丢掉、或按实时几何覆盖一次。
真正依赖它判定的只有 bounds；缩放从 fix175 起完全绕开。

### 坑
⚠ 手测时用 `su -c 'echo ... | tee /data/system/memoryfreeform_window_scale'` 建的文件
owner=root、SELinux 标签不对，**system_server 写不进去**（chmod 666 也不行）。
必须删掉让 hook 自己建（`-rw-r--r-- system system`）——真实场景本就如此。

175 已构建安装 + 重启（versionCode=175），待用户验证手感与可靠性。

## fix171：确认「拖边角不改 bounds」→ freeformScale 取证探针

用户报"还是不行"。高频轮询（300ms × 260 次）+ 探针日志显示：用户**按住拖了 6.4 秒**，
Task bounds **一像素没变**（`[125,582][1205,2310]` 全程恒定），所有 setBounds/onResize 帧
`szChg=false`。**不是记录端丢尺寸，是拖边角根本不产生 bounds 变化。**

0.70（MIUI_LAYER_SCALE）就是这个 scale 的默认档（dumpsys 快照 `mFreeformScale=0.7` 同源铁证）。

## fix177：边界判定改用**实际缩放** + 左右两侧留安全距离（未验证，等真机）

### 用户诉求（两条）
1. 「边界判定现在有问题了，实际显示大小与边界判定不一致」
2. 「边界左右两边也留一些安全距离」

### 根因（1）
三处钳制（App `miuiDeliveryRect` / 复核块、`BirthHook.fit`、`RecordHook.doWrite`）
全都**恒用 0.70**（`HookBridge.miuiLayerScale()` / `LAYER_SCALE`）换算"视觉宽高"。
但 0.70 只是 freeformScale 的**默认档**，拖边角之后实际是 0.45/0.55/0.91。
用 0.70 去算 → 一个实际只有 694px 宽的窗被当成 1080px 满屏宽 →
`maxLeft = sw − 视觉宽 = 0` → **每次重开都被强行吸到左边缘**。
离线复算实证：bounds[400,…] 宽1543、scale=0.45
 - 新口径 → left 保住 354（视觉 354..1048，两侧留 31）✅
 - 旧口径 → left 被压成 0 ❌（正是用户看到的现象）

### 改动
- `WindowSizing`：
  - 新增 `SIDE_SAFE_DP=12` / `sideSafePx(ctx)` / `sideSafePx(density)` / `sideSafeSystemPx()`；
  - `fitBounds` / `clampRect` 新增 `sideSafe` 参数：宽度上限扣两侧、
    `l = rect[0].coerceIn(side, max(sw−side−视觉宽, side))`；
    ⚠ `side` 必须 `coerceAtMost((sw-1)/2)`，否则满宽窗时 min>max，`coerceIn` 直接抛异常。
  - `scale` 参数注释改成"必须传本次真正生效的缩放"。
- `HookContract.effectiveScale(pkg, landscape)`：记忆缩放 → 缺省 `MIUI_LAYER_SCALE`。
- `CornerWindowService`：`readSystemWindowScale()`（root cat，App 直读 /data/system 恒失败）
  + `effectiveScale()` + `sideGapPx()`；`miuiDeliveryRect` 与复核块都改用它们。
- `MiuiFreeFormBirthHook.fit()`、`MiuiFreeformRecordHook.doWrite()`（两处 clampRect）
  改用 `HookContract.effectiveScale` + `WindowSizing.sideSafeSystemPx()`（三侧同口径）。
- 删除 fix176 遗留死代码 `foldScaleIntoBounds`（零调用方，且它引用了未导入的 `roundToInt`
  导致编译失败）。
- 版本 `versionCode=177 / 1.0.177`，`assembleDebug` BUILD SUCCESSFUL。
